# WH-1000XM4C support

This fork was created by [@PawDD](https://github.com/PawDD), an XM4C owner, to add the macOS controls missing from the upstream version tested during development. WH-1000XM4C is a distinct 2026 model based on the established WH-1000XM4 design from 2020, with updated sound tuning and ten-band EQ; the similar name and appearance do not make their control protocols interchangeable. See the [manufacturer announcement](https://www.sony.co.uk/presscentre/sony-introduces-wh-1000xm4c-wireless-noise-cancelling-headphones-and-updates-popular-mid-and-entry-level-wireless-headphones-with-wh-ch730n-and-wh-ch530).

This fork extends SonyBridge v0.4.0 (`d0ecd561ebf6f1cb87ffbf29528107b2221724d5`) for the refreshed WH-1000XM4C, using Sony's v2 protocol. The original v1 WH-1000XM4 and the XM4C must not be conflated. The Bluetooth connection implementation, application permissions, pairing and upstream startup preferences are retained. Local injection libraries, automatic hardware probes, raw captures and local compiler workarounds are excluded.

## Capability selection and packet layouts

The `06 00` / `07 00` control capability list is cached per connection. XM4C commands use advertised function IDs rather than assuming an XM6 layout. A malformed capability reply does not authorize guessed writes. Unsupported Adaptive Volume is not probed.

| Feature | Advertised function | Commands and payload interpretation |
| --- | --- | --- |
| ANC / Ambient | `6a` | GET `66 16`; SET `68 16 01 <effect> <NC/ASM> <single/dual> <voice> <level>`. The separate NC byte is required. |
| Ten-band EQ | `57` | GET `56 04`; SET `58 04 <preset> <count> <bands>`. Ten raw values in `0..12`, with no separate Clear Bass slot. |
| EQ preset list | EQ capability inquiry | GET `50 04 01`; RET `51 04 <bands> <steps> <count> { <ID> <name length> <name> }`. Language `01` requests English; firmware 1.1.2 returns empty names. |
| Speak-to-Chat | `f2` | Type 1: GET `f6 02`; SET `f8 02 <enabled-inverted> 01`. This is not the type-2 `0c` layout. |
| Speak-to-Chat timing | Type-1 capability and extended state | GET `f0 02` provides three timeout durations; GET `fa 02` reads sensitivity, voice focus and timeout; SET `fc 02 <sensitivity> <voice focus> <timeout>`. |
| DSEE | Existing v2 layout | GET `e6 01`; SET `e8 01 <enabled>`. |
| Auto power-off | Existing wearing-aware layout | GET `26 05`; SET `28 05 <current option> <last timer option>`. Current selection and remembered timer are distinct. |
| Connection priority (read-only) | `e1` or `e3` | `e1` selects subtype `00`, `e3` selects `02`; GET `e6 <subtype>` / RET `e7 <subtype> <priority>`. `00` quality, `01` stability. |
| Codec status (read-only) | Existing v2 status inquiry | GET `12 02`; RET `13 02 <codec>`. `00` negotiating, `01` SBC, `02` AAC, `10` LDAC. |

## Equalizer behaviour

Firmware 1.1.2 advertised IDs `00`, `30`, `31`, `32`, `33`, `20`, `a0`, `a1`, `a2`. Empty names use the labels Off, Heavy, Clear, Hard, Soft, Gaming, Manual, Custom 1 and Custom 2. Nonempty device names are preserved; unknown IDs get a numeric label. The main window and menu-bar panel share the same list. Discovery failures retain the conservative Off/Manual fallback rather than substituting unsupported five-band presets.

Selecting Manual retains the current curve, as in the existing UI. Selecting Custom 1 or Custom 2 loads the saved curve. All three expose sliders. Writes retain the selected preset ID, and numbered-slot writes require a discovered XM4C preset list containing that ID. The read-back checks the preset and every band. Rapid edits are coalesced without toggling button appearance; a preset selected during an edit waits for the pending curve writes to complete.

## ANC variants and speech timing

Subtype `16` uses NC value `01` for single (Wind Noise Reduction) and `02` for dual (Noise Canceling). A valid state reply exposes the selector while ANC is active, in both macOS views. Variant-only changes count as pending writes and are not erased by a stale poll. Failed writes discard pending state so subsequent polling can resume.

The speech timeout choices are `00` fast, `01` medium, `02` slow and `03` no automatic close. Durations come from the headphone capability reply. The UI appears only after both capability and extended-state replies validate. A timeout SET uses a fresh read to preserve sensitivity and voice focus; malformed reads block the write. The application does not substitute guessed default values.

## Confirmation and codec reporting

A transport ACK confirms receipt, not application. On XM4C the macOS bridge sends each SET once and repeats fresh GETs until the requested state is observed or a monotonic deadline expires. A read/transport error propagates instead of confirming the optimistic cache. Individual inquiries validate their payloads. The deadline is checked between transport operations; it does not preempt a blocked transport read. Other models retain the upstream write-confirmation policy.

Connection priority is **read-only on macOS**. Its title occupies its own line, followed by `Read-only on macOS` and a disabled menu aligned to the right. The refresh button reads priority and headset-reported codec without sending SET. No connection-priority write API is exposed by this fork. The separate `e7` Classic/LE Audio function is unsupported rather than guessed.

A development build exposed a transient Negotiating → SBC → AAC sequence when connection priority was changed on a Mac. Changing priority was therefore removed from the fork's UI and protocol API. This observation does not establish a firmware bug or a general macOS codec restriction. A headset-reported codec alone does not identify the active host in multipoint. Failed or unknown codec reads clear the stale value rather than showing it as current. `Negotiating` is a device status, not a codec choice.

## Validation scope

| Evidence | Scope |
| --- | --- |
| Development hardware observations | XM4C firmware 1.1.2, Apple Silicon Mac: basic ANC/Ambient, one Manual EQ band, DSEE, Speak-to-Chat on/off and auto power-off were changed, read back and restored. All nine preset IDs were read. |
| Prior clean CI-built development app | Off, Heavy, Clear, Hard, Soft and Gaming matched preset IDs and ten-band replies in a hardware smoke test. |
| Installation report | The maintainer confirmed that the application works locally and that the DMG prepared from source revision `5d98a6e` installs successfully on their Mac. This is an installation/usability report, not an exhaustive per-feature verification. |
| Automated regression tests | Capability gating, ANC byte offsets and single/dual state, ten-band EQ, independent Custom 1/2 fixture storage, malformed replies, rejected unsupported presets, preserved speech parameters, timeout choices, delayed application, read errors, read-only priority/codec discovery and preset labels. Fixtures are reconstructed samples, not captured sessions. |
| Still requiring a current-commit hardware retest | Custom 1/2 persistence, speech timeout, Wind Noise Reduction with separately recorded per-feature hardware results. Passing fixtures do not count as hardware verification. |
| Multipoint and control handover | The maintainer exercised multipoint switching/reconnection and verified correct device names after handing control between SonyBridge on Mac and Sound Connect on Android, on XM4C firmware 1.1.2. |
| Unverified | Other XM4C firmware, Windows/Linux hardware behaviour and new-feature UI parity, experimental playback switching/fixing and microphone/voice-profile transitions. |

The existing XM4 v1, XM6, conformance, metamorphic and macOS connector regression suites are retained. CI builds the native macOS application for arm64 and x86_64, and builds/tests the CMake client with native compilers on Linux and Windows. No stable or cross-platform hardware compatibility claim is made from compilation alone.

## Build and tests

- `sh Client/tests/run-portable.sh`: C++ protocol, conformance, metamorphic and write-readback tests.
- `sh Client/tests/run-macos.sh`: the above plus offline macOS receive-buffer and Swift preset-presentation tests; it does not open a Bluetooth connection.
- CMake: configure with `-DSONYBRIDGE_BUILD_PROTOCOL_TESTS=ON`, build, then `ctest --test-dir Client/build -C Release --output-on-failure`.
- Full macOS app: run `sh Client/macos/build-release.sh` from a clean checkout with full Xcode selected. This builds both architectures from the checked-out source and packages the resulting app; it never reuses an installed application. CI runs `Client/macos/package-dmg.py` to produce `SonyBridge XM4C.dmg` and a SHA-256 file. The script embeds licenses, signs with release entitlements (no debugger entitlement), verifies unchanged executable code/data for both architectures, and mounts/verifies the DMG without launching the app. The version stays unchanged for a packaging-only update. Artifacts are uploaded for testing; publication of a release is a separate action.
